# Journal 文章写作与开发规范

MYVIPSERVICE 的 Journal 是编辑向长文内容——`src/content/journal/{en,zh,fr}/<slug>.md`，渲染模板固定为 `src/pages/[locale]/journal/[slug]/index.astro`。用途是 SEO 长尾流量和品牌叙事（目的地攻略、体验故事、季节性专题），不是产品页，不直接卖东西，但**要真的有用、有具体信息**，不是空洞的软文。

## 一、这不是"要求四语言同步"的内容

- CLAUDE.md 明确写着：Journal 一类"搜索型内容"允许语言之间不同步——一篇内容只服务需要它的市场，不必翻译四遍。写新文章时不需要一次性把三语都写完，可以先写目标市场最需要的那一两种语言。
- 但凡是已经存在的三语版本，彼此之间仍然要保持"同一篇文章"该有的一致性（标题指向同一件事、图片同一套逻辑），不是"允许不同步"就可以内容各写各的。

## 二、图片：封面图决定文章质量的第一印象，不能是随手一张

- 渲染模板 `<Gallery images={data.gallery.length > 0 ? data.gallery : [data.coverImage]} />` 会在 Hero 之后、正文之前**整版展示**封面图/相册，是读者点开文章第一眼看到的大图，权重和体验页面（见 [[体验写作]]）一样高，不是缩略图角落的小图。
- **封面图应该是文章主题的具体画面，不是最方便找到的通用风光片**——CLAUDE.md 已经明确写了"避免游客照片式陈词滥调构图（如埃菲尔铁塔仰拍）"，这条对 Journal 封面图同样适用，甚至更重要：一篇讲"如何为孩子挑选体验"的文章，封面若是大本钟这类地标仰拍照，虽然不算文不对题（文章确实讨论伦敦），但没有真正传达"亲子""体验挑选"这个主题——优先找画面里有"正在发生的具体场景"的图（家长带着孩子在博物馆里、私人向导蹲下来跟孩子说话），没有的话退而求其次用目的地实景，但要清楚这是退而求其次，不是首选。
- `gallery` 数组里的每一张图同样要经得起"画面内容和文章在讲的事情对得上"的检验，参考 [[体验写作]]"一"里"选图前先问画面本身能不能让人猜到主题"的方法。
- 文章里提到的 `relatedExperienceKeys`/`relatedAccommodationKeys` 等关联内容，会在文章底部以卡片形式展示，卡片图用的是**那个关联内容自己的 `coverImage`**——如果某个体验/住宿自己的封面图本身有问题（比如 [[体验写作]]"一"里那次真实 bug：伦敦亲子博物馆体验的封面图是完全不相关的海滩照），这个问题会跟着关联卡片一起出现在每一篇引用它的 Journal 文章里。**改 Journal 文章时如果发现底部关联卡片图不对，先去检查是不是被关联内容自己的封面图拖累的，根源修复那边，不要只在 Journal 这一层想办法绕过去。**

## 二.5、正文必须图文穿插（第一条硬规则，不能只靠顶部相册）

- **顶部 `gallery` 不算图文穿插**——它是 Hero 之后的整版展示，正文里仍然必须有图。2026-10-06 踩过的真实返工：Ducasse sur Seine 文章三语正文一张图都没有，只有顶部相册，用户直接指出"没改"。酒店文章同理，不能因为"相册已经有图"就把正文写成纯文字。
- **正文已经图文穿插了，顶部就不要再堆一排图**：顶部只留封面一张（`gallery` 留空数组，模板会自动回退成只显示 `coverImage`；或只放一张），不要把四五张图整排摆在 Hero 下面再在正文里又摆一遍。顶部相册只在正文确实没法配图的极少数情况下才保留多张。原因：读者往下滚才是看正文的时候，正文里的图本来就在讲同一件事，顶部再堆一堆只会让页面头重脚轻、拖慢首屏、也让正文里的图显得是重复内容。**同一张图不要既出现在顶部相册又出现在正文里。**
- **写法**：正文里直接用 Markdown 图片 `![描述](/images/xxx.jpg)`，渲染走 `.prose img`（4:3 裁切填充，全站统一，不单独调尺寸）。图紧跟对应的那一段文字，不是文字堆在一起、图片堆在文末。
- **密度**：每个 `##` 小节至少一张图；一节里有两个并列的具体对象（如午餐班次/晚餐班次），各配一张，紧跟各自段落。只有纯"怎么预订/常见问题/收尾"这类没有可视对象的小节可以不配。
- **图的来源优先级**：先用站里已登记的图（`image-attributions.ts`，关联酒店/体验自己的图可以复用），再去 `~/Desktop/Eva 工作/图片资源库/` 找（合作方提供原图、宣传册提取原图），最后才是新搜索 Unsplash/Pixabay。新引入的图必须同时登记 `src/data/image-attributions.ts`（含三语 alt）和 `docs/image-asset-register.md`。
- **宣传册提取的图多是竖版小图**：正文是 4:3 裁切，竖图直接塞会被硬切、放大后发软——用 PIL 先按 4:3 裁好（选好垂直焦点）再存进 `public/images/`，并在 notes 里写 "Cropped to 4:3"。分辨率不够的如实告诉用户，不要假装清晰。
- **不要给图编具体身份**：不确定这张图拍的是哪个具体房间/空间/菜品时，alt 和说明只写画面里确实看得见的东西（"沿玻璃墙摆开的长桌"），不要写成"主厨餐桌""Le Carré"这类要核实的具体名称。
- 三语版本正文图片位置和张数保持一致，alt 各自本地化。

## 三、内容结构

`content.config.ts` 里 journal 的字段：

- `category`——十个固定单选枚举（Destination Guides / Hotel Inspiration / Private Experiences / Family Travel / Food & Dining / Seasonal Travel / Art & Culture / Fashion & Shopping / Travel Advice / MYVIPSERVICE Stories），不新增分类、不做自由标签（自由标签容易产生近义重复，见 `taxonomy.md`）。
- `excerpt`——列表页卡片和 SEO description 的兜底文案，一句话说清楚"这篇文章要回答什么问题"，不是标题的同义重复。
- `author`——**可选字段，没有真实作者就留空，不虚构人名**（`content-architecture.md` 里明确写着"当前内容均未填"，这是刻意的，不是漏填）。
- 正文（Markdown body）——模板会自动生成阅读时长估算（中文按字符数/400，英法按词数/200）和目录（`## ` 二级标题数 > 1 时才显示侧边栏 TOC）。**用 `##` 组织正文小节，不只是为了排版好看，是真的会驱动 TOC 是否出现**——一篇文章如果只有一个大段落没有分节，读者连侧边导航都看不到。
- `relatedDestinationKeys`/`relatedAccommodationKeys`/`relatedExperienceKeys`/`relatedJourneyKeys`——只关联真实存在、发布状态的内容，不要写一个还不存在的 translationKey 进去（会被 `resolveRelated` 静默过滤掉，不报错，但等于白写）。
- `relatedTravelStyleKeys`（2026-09-23 新增字段，详见 `travel-audience-segments` skill"四.2"）——只在内容上真的贴合某个已上线人群时才打，不强行凑数，允许留空。这是一个**正向字段**（文章自己声明和哪个人群相关），不是从别处反查来的，所以打标签这个动作只能靠人工判断内容是否贴合，没有自动化检测。

## 三.5、文章里嵌入咨询表单（`enquiryForm` 前置字段）

- 目前支持 `enquiryForm: 'ducasse-dinner'`（餐厅晚宴咨询）和 `'hotel-stay'`（酒店咨询，勾选的酒店来自文章自己的 `relatedAccommodationKeys`）。模板在正文之后渲染 `<section id="enquiry">`，所以文章开头放一句跳转链接 `[…](#enquiry)`，结尾放"怎么预订/怎么咨询"小节，说清楚要填什么、"我们会在 24 小时内联系您"。
- 表单本身遵守 `产品表单` skill（两栏 + 吸顶汇总 + 分步、汇总只放选择项）。新增一种表单 = 新组件 + schema enum 加一个值 + 模板里加一个分支，不要在模板里硬编码 slug。
- 文案里提到表单位置要核对："下方"——表单确实在正文之后。
- 酒店咨询走 `notify-accommodation-lead`（进后台订单）；Ducasse 晚宴走 `notify-dining-lead`（只发邮件，不建订单）。

## 四、写作风格与真实性

- 不编造统计数字、客户案例、奖项或第三方认可——如果要引用一个具体的门槛/建议（比如"提前 2-3 周预订"），这类建议应该来自真实的业务经验或已经在其他内容里确认过的信息，不是为了让文章看起来更权威而现编一个数字。
- 中文不是机械翻译：侧重实操信息（微信联系方式、中国家庭常见顾虑、儿童双床/连通房这类具体安排）。法文侧重服务标准与专业度表述。
- 撇号/引号：字符串只含撇号（没有其他引号符号）时，整条换双引号，不用 `\'` 转义——`\'` 在 YAML 单引号字符串里不合法，这是全站反复出现过的真实 bug，写完跑 `grep -n "\\\\'" src/content/journal/*/*.md` 自查。
- **2026-09-23 踩过的反向坑**：如果一条字符串里同时有撇号（如 `shouldn't`）**又**有作为强调引用的双引号（如 `"family-friendly"`），手动把整条换成双引号包裹、内部撇号不转义，看似更统一，但 `npm run format:check` 跑的 Prettier 会把它**自动改回单引号 + 双写撇号转义**（`shouldn''t`）——因为这种情况下单引号+双写转义所需的转义字符比双引号+转义内部引号更少，Prettier 按"转义最少"选定界符，不是随手选的。`''` 双写撇号本身是合法 YAML（不同于 `\'`），**这种情况下不需要手动去"纠正"成双引号，改了也会被 Prettier 格式化跑回去，纯属做无用功**——只要 `format:check` 是绿的，就不用管撇号具体是用单引号双写还是双引号包裹哪种形式。
- 不能出现暴露内部工作状态的话（"我们会陆续整理成独立页面"这类）。

## 五、验收

- [ ] **正文每个 `##` 小节（除预订/FAQ/收尾外）是否都有紧跟段落的配图**——只有顶部相册、正文纯文字 = 不合格（见"二.5"）；三语张数和位置是否一致；新图是否已登记 attributions + register，竖图是否已按 4:3 预裁。
- [ ] **顶部是否只留封面一张**——正文已图文穿插的话，`gallery` 应为空或单张，不能顶部堆一排图；顶部的图不能和正文里的图重复（见"二.5"）。
- [ ] 封面图（及 gallery，若保留）画面内容是否真的对应文章主题，不是方便但空泛的风光/地标照——参考"二"的判断方法。
- [ ] 文章引用的关联内容（体验/住宿/目的地/行程）自己的封面图有没有问题——有问题优先去源头修，不在 Journal 这一层绕过去。
- [ ] `category` 是否用了十个固定枚举之一。
- [ ] `author` 是否为空或者是真实存在的人——没有真实作者就留空。
- [ ] 正文是否用 `##` 分了节（影响阅读时长估算准确性和 TOC 是否显示）。
- [ ] 关联的 `relatedXxxKeys` 是否都指向真实存在、已发布的内容。
- [ ] `relatedTravelStyleKeys` 是否只在真正贴合时才打。
- [ ] 有没有编造统计数字、客户案例或第三方认可。
- [ ] 如果嵌入了 `enquiryForm`：开头有 `#enquiry` 跳转、结尾有 24 小时联系说明、浏览器里跑通分步校验和汇总卡片（三语 + 移动端）。
- [ ] `npm run format:check && npm run lint && npm run check && npm run build` 全绿，浏览器里确认无控制台报错、无缺图。
