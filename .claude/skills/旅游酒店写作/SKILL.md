# 旅游酒店写作规范

MYVIPSERVICE 的酒店/住宿页面是 `src/content/accommodations/{zh,en,fr}/<slug>.md`，渲染模板固定为
`src/pages/[locale]/accommodations/[slug]/index.astro`。一家物业一次做完（素材→图片→内容→三语→验证部署→预订通道），不要多家同时铺开。

## 一、素材收集

- **文字和图片一起收集，不要分两遍做**：逐页打开官网（客房页、套房页、餐饮页、水疗页、独栋别墅/木屋页、历史故事页），同一页里顺手把事实和图片 URL 都记下来，不要先把所有文字写完再回头找图——那样容易漏配图，也容易需要返工。
- 去官网多个页面交叉核实，不能只看一页就下结论。
- **信息冲突时标出来问用户，绝不自己编**——例如房间数量、餐厅名称等不同来源说法不一致时，优先信任最新鲜、且被多次独立确认的信息源（如官网实时页面），并诚实告知用户这个判断依据（"这可能是最近改名/改造"之类），而不是悄悄选一个。
- **冲突严重到物业身份本身对不上时（不是数字对不上，而是整页写的根本是另一处物业——例如页面标题是某餐厅，但这个餐厅其实是同集团另一家酒店内部的附属设施，或该餐厅已被替换/关停），用 AskUserQuestion 正式停下来问用户**，给出 2-3 个处理方案（如"改写成真正的那家物业页""保留原样但更新过时信息""下线该页面"），不要自己决定；用户选定方案后要执行到底，包括下面这份清单里的所有交叉引用。
- **物业改名/身份纠正时的完整更新清单**（当 slug 或整体身份需要换掉时）：
  1. 三语内容文件重新创建（旧文件删除，新 slug 建三个新文件）。
  2. 搜索并更新所有引用旧 slug 的地方：其他住宿页面的 `relatedAccommodationKeys`、目的地页面（`destinations/*.md`）里列出的住宿 slug 数组、`admin/orders.astro` 的 `PROPERTY_CONTACTS`。
  3. 跑 `npm run build` 后确认 `dist` 里旧路由已经不存在、新路由已生成。
  4. 浏览器里检查引用旧物业的关联卡片是否正确指向新物业。
- **引用某个页面的信息前，确认这个页面真的还在线**——有些旧链接（历史文章、搜索引擎缓存、其他网站转载）会跳转回官网首页而不是报错，说明内容已下线/改版，不能当作当前事实来源；标题栏显示的是首页标题就是信号。
- 不虚构客户数量、星级、奖项、合作关系——没有确认授权的内容不能上线。
- 动手前先查 `src/data/image-attributions.ts` 和 `public/images/` 里有没有这家物业已经下载过的图（比如之前写 Journal 文章时顺带下载过的封面图），避免重复下载同一张图。
- **找不到官网、无法公开核实的私人未挂牌房源**（纯靠业主/中介直接合作，搜索多次也找不到对外挂牌页面）：不要为了"配齐内容"虚构设施细节或强行找一张不相关的图冒充这家物业。按"私人合作房源"的口径写——`description`/`highlights`/`servicePerspective` 里诚实说明这是直接与业主对接、非公开挂牌，具体房间配置、价格、空档情况需要客人提供**行程日期、团体人数、具体需求**后由顾问直接向业主确认；`familyNotes`/`diningWellness` 这类字段也改成主动邀请客人提供这些信息的口吻，而不是套用万能话术硬编。已经掌握的真实基础信息（如卧室数、地理位置，这类通常是业主/中介提供的）可以保留使用；找不到实拍图时维持现有占位图即可，不要为了有图而误用不相关素材。

## 二、图片

**总原则：文章中能找到对应图片的都要有图片。** 不是挑几个重点配图就够了——正文里提到的每一个具名的东西（每一家餐厅、每一间水疗、每一款特色房型），只要官网能找到对应照片，就必须配图，不能因为"已经有别的图了"就跳过。比如一家酒店有 3 家米其林餐厅，就要 3 家都配图，不能只给其中一家配图、其余两家纯文字带过。

- **先主动去官网找图片，不要等用户给。** 官网的客房页、套房页、餐饮页、水疗页、独栋别墅/木屋页通常都带高清实拍图（多是专业摄影师署名作品，不是 3D 效果图——3D/non-contractuel 标注的图不能用）。能找到对应图片的段落就要放图，覆盖面尽量全：外观、内部设计、餐厅、水疗、每个挑出来重点介绍的特色房型都尽量配图，不要只放一张封面图就了事。用户批准/审核仍然发生在 `usageStatus: 'pending-approval'` 这一步，主动下载不等于跳过审核，只是不让草稿卡在等图片上。
- 用 Browser 工具打开对应页面，读取真实的 `<img>`/背景图 URL（很多站点图片是懒加载或背景图，直接看 DOM 而不是猜文件名），用 curl 下载到 `public/images/`，命名规则跟已有图片一致（`accommodation-<slug>-<主题>.jpg`）。
- **遇到 Cloudflare/反爬拦截时的下载解法**：如果 curl 下载下来的 `.jpg` 实际是 HTML（用 `file <name>.jpg` 检查会显示 "HTML document text" 而不是 "JPEG/PNG image data"，说明触发了 Cloudflare "Attention Required" 验证页），改用 Browser 工具的 `javascript_tool`，在浏览器页面自身的上下文里执行 `fetch(url).then(r=>r.arrayBuffer())` 再转 base64（这个浏览器 tab 已经是通过验证的真实会话，能绕开拦截）。这个调用会因返回内容超出工具输出上限而报错，但报错信息会给出一个本地文件路径，完整的 base64 结果已经存在那个文件里——读取该文件、去掉尾部的 `(captured at origin ...)` 标记和包裹引号，`base64.b64decode()` 后写成真正的图片文件。同时注意有些图实际是 WebP 格式（`file` 检查会显示 "Web/P image"，即使文件名后缀是 `.jpg`）——用 macOS 自带的 `sips -s format jpeg <in> --out <out>` 转成真正的 JPEG 再登记，不要把 WebP 内容当 JPEG 直接用。
- 图片来自官方素材库时，核对图片文件名/URL 路径是否对应正确的物业——集团旗下常有多处姊妹物业（如 K2 Palace/K2 Altitude、Ultima Collection 旗下多处别墅共用同一站点结构，各自图片带不同的物业前缀代码），用常识核实，混入其他物业的图片要排除。
- 图片下载后登记进 `src/data/image-attributions.ts` 和 `docs/image-asset-register.md`，标记 `usageStatus: 'pending-approval'`，等用户批准；来源写清楚真实 `sourceUrl`（指向官网对应页面）。这两个文件要保持一一对应——如果用户要求"统一整理图片存储"，先核对 `public/images/` 里的文件和这两处的登记条目是否完全对得上（每张下载的图都登记了、每条登记都有对应文件在），清理掉损坏/无用的下载残留（如反爬拦截产生的假图片文件、临时目录里的下载草稿），而不是重新设计整套存储结构——现有体系只要保持一致就够用，不必为了"整理"而大改。
- 避免游客照片式陈词滥调构图（如地标仰拍），优先建筑细节/房间/餐桌/私人空间这类"正在经历它"的画面，人物尽量少出现；如果某个招牌设施（如私人影院）官网只有含人物的体验类照片、没有空场景照片，可以用，但要在登记的 `notes` 里说明"这是唯一可用的这个空间的照片，含人物而非空场景"。
- **图文穿插**：图片紧跟对应文字段落，不是文字堆一起、图片单独扔一堆。复用 `MediaHighlightList.astro` 组件渲染（`{text, image?}` 数组），不要发明新的图片布局。
- 图片尺寸全站统一（4:3 比例、裁切填充，走 `.prose img` / `.figure--standard` 全局规则），不要单独调整某一页的图片大小。
- 只有官网确实找不到对应图片（比如某个很小的细节、或官网图片质量太差/带水印）时，才需要向用户要图或说明缺口，不要默认等用户供图。
- **不要在同一页面重复用同一张图，尤其是 `highlights` 第一条最容易踩坑**：物业介绍的开篇段落经常想配外观图，但这张往往就是 `coverImage` 已经用过的那张——`coverImage` 已经在"房源概览"里展示过一次，`highlights[0]` 如果又设了同一个 `image` id，这张图会在页面上重复出现两次。**写完 highlights 后自查**：`grep` 一下 `coverImage` 的图片 id 在整个文件里出现了几次，正常应该正好两次（一次在 `coverImage:`，一次在 `gallery: [...]` 里）；如果在 `highlights` 或 `roomTypes` 里又出现第三次，说明重复了——开篇段落要么不配图（反正封面图刚展示过，视觉上不缺），要么换一张角度或时段不同的外观图。三语文件都要各自跑这个自查，不能只查中文。
- 米其林餐厅、招牌菜这类"有名气"的内容值得多配一张图（餐厅环境+菜品各一张），把它在页面里做突出，不要只放一张就带过。
- **图片下载后先用 Read 工具打开确认再登记/引用**——排除三种情况：文件损坏或下载到的是错误页面（非图片内容，含前面提到的 Cloudflare 验证页）、3D 效果图或明显带水印、图片实际内容对不上文件名（例如混入姊妹物业）。确认没问题再写进 `image-attributions.ts` 和内容文件。

## 三、页面内容结构（模板已固定，新页面自动套用）

`content.config.ts` 里 accommodations schema 的字段对应关系：

1. **房源概览**（`description` + `coverImage`）——简介+封面图。
2. **酒店特色**（`highlights`）——图文穿插的流畅叙述，不是生硬的要点罗列。设计、服务、设施等混在一起写成自然段落，不必分小标题。
3. **房型**（`roomTypes`）——**房型多寡决定详略**：
   - 房型种类少（大多数精品酒店/度假村/私人别墅，几套到十几套）：每个房型一张图+一段描述，逐一介绍。
   - **房型种类多的大型酒店**：只挑有代表性/招牌的特色房型（套房、顶层、有特殊景观或设计亮点的房型）做完整的图+文介绍；其余常见标准房型（标准间、高级间这类各家都有的常规房型）合并成一段简单描述带过（面积区间、床型选择、主要差异），不用每个房型单独配图配段落。
   - **挑特色房型时，优先选有名人/历史光环的那些**：很多老牌宫殿酒店会有以名人命名或设计的套房——比如丽兹巴黎的可可·香奈儿套房（她在那住了二十多年）、克里雍酒店由 Karl Lagerfeld（"老佛爷"）亲自操刀设计的大公寓、以玛丽·安托万内特或其他历史人物命名的套房。这类故事比单纯报面积、报设施更有记忆点，官网的套房介绍页通常会写这些渊源，挖出来用，不要漏掉。
4. **MYVIPSERVICE视角**（`servicePerspective`）——收尾段落，说清楚"谁适合住这里"，也要诚实说"谁可能不适合"（例如空间较小的酒店应该明确写给不需要太多公共空间的小家庭/情侣，大团组应考虑别的选择），不是一味吹好话。

**定位（`positioning`）诚实度**：不要默认给所有物业都打上 Luxury/Palace 标签——先看官网自己怎么定位（几星级、官网标题/文案里是否自称"4 star hotel"这类），精品/舒适档次的物业用 `Boutique` 更准确，不要为了"听起来高级"而夸大档次。`servicePerspective` 收尾段落里也要诚实写清楚"如果想要更高规格/更大公共空间，可以看 XX"，主动给出同目的地里更高档的备选，而不是含糊带过或只说好话。

## 四、写作风格

- **正文含英文/法文人名地名撇号（如 L'Orangerie、d'exception、Tessier's）时，这一条 YAML 字符串要用双引号包裹，不要用单引号+反斜杠转义**——`\'` 在 YAML 单引号字符串里不是合法转义，`astro check` 会报 "bad indentation" 之类的误导性错误。正确写法是整条换成双引号 `"..."`，字符串内部的撇号不需要转义。这个错误几乎每次含撇号的物业页都会踩一次，写完先跑 `grep -n "\\\\'" src/content/accommodations/*/*.md` 自查。
- **反过来，中文正文里用直引号强调词语（如"以假乱真"）时，这条 YAML 字符串要用单引号包裹**，不能用双引号——道理相同，双引号字符串内部不能再出现未转义的双引号。两条规则一起记：字符串内部出现哪种引号，外层就换成另一种；写完用 `grep -n '"' src/content/accommodations/*/*.md` 扫一遍确认外层引号类型都选对了。
- 中文版不是机械翻译，要有自己的语言组织，避免生硬、说明书式的口吻。
- 不能出现暴露内部工作状态的话（例如"我们会陆续整理成独立的酒店页面"这类）。
- 价格话术统一用"价格需咨询"，不用"价格面议"（听起来像讨价还价）。
- 要有真实细节支撑（历史沿革、具体数据如泳池尺寸、房间面积、餐厅历史），不是空洞形容词堆砌。

## 五、三语同步

- 中/英/法内容意思对应，但不是逐字翻译，各语言可以有不同侧重。
- 中文侧重实操信息（微信联系方式、中国家庭需求、儿童双床等）。
- 法文侧重服务标准、国际客群、当地专业度。

## 六、独立预订通道（如该物业需要单独预订入口，而非走通用联系页）

- 表单尽量简单：人数、入住/退房日期、联系方式，加上该物业特有的勾选项（例如是否需要完整雪季规划/可替换酒店这类）。
- 走"先询价"模式：客人提交 → 后台生成 `quote_requested` 订单 → 人工确认后手动发送真实报价链接，不是即时下单付款。
- 需要新建：`accommodations/<slug>/book.astro` 页面 + booking widget 组件 + `notify-accommodation-lead` 类 netlify function + `admin/orders.astro` 里对应板块。

## 六.5、联系方式登记（有对外公开预订部门的物业都要做，不限于有独立预订通道的）

- 素材收集时顺手把物业的**预订部门**（reservations，电话+邮箱）和**咨询部门**（info，邮箱为主）都找到，登记进 `admin/orders.astro` 的 `PROPERTY_CONTACTS`（按 slug 建 `{ reservations: {phone, email}, info: {email} }`），方便后台工作人员直接联系确认，不用临时现查。
- 官网的"Contact"/"Press"/页脚一般能找到；找不到 info 邮箱时预订部门的也够用，不必强求两个都有。
- **私人别墅/无独立预订部门的房源不强制登记**——这类走通用"联系我们"询价流程即可，不需要在 `PROPERTY_CONTACTS` 里单独建条目。

## 七、验收

在跑验证命令前，先对着页面自查一遍图片，这几项容易第一遍就漏：

- [ ] `highlights`/`roomTypes` 里能配图的条目是否都配了图（不是只有封面一张）。
- [ ] 全页面（含 `coverImage`）有没有重复用同一张图——按上面"图片"一节的方法 grep 一下 `coverImage` 的图片 id，确认只出现两次。
- [ ] 米其林餐厅/招牌菜/最具辨识度的房型这类"值得炫耀"的内容是否配了不止一张图。
- [ ] 三语（zh/en/fr）的图片、房型详略取舍是否一致（不是只改了中文）。
- [ ] 若这次涉及新的 `type` 枚举值（如 `château`/`estate`/`resort` 等 accommodations schema 里定义但之前没实际用过的类型），检查 `src/i18n/ui.ts` 三语区块里是否都已经有对应的 `type.<value>` 翻译键——漏翻译会导致"住宿类型"字段和页面 eyebrow 标签在页面上空白，这是实际踩过的坑。

自查完再跑：

- `npm run format:check && npm run lint && npm run check && npm run build` 全绿。
- 桌面+移动视口都要看。
- 浏览器里实测一遍确认功能正常、无控制台报错、无缺图。
- 部署到线上生产环境前跟用户确认一次（生产部署属于高风险操作，不能自行决定）——除非用户在当前对话里已经给过范围明确的授权（例如"这一轮都做好直接部署，不用每次问"），那按授权范围执行即可，但授权仅限该轮对话/该项任务，不要当成永久默认。

**本地开发排查**：如果本地预览时所有 accommodation 页面（包括已经上线正常的）突然全部 404，且 `.astro/dev.log` 里能看到 `data-store.json.tmp` 相关的 rename 报错，说明是内容集合缓存损坏，先执行 `npx astro dev stop && rm -f .astro/data-store.json.tmp && npx astro dev --background` 重启，不要误以为是内容文件本身写错了。
